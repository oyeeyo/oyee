## 2. 一次完整提问的全流程（端到端）

让我们追踪一次完整的用户提问，看看数据在各个模块间如何流转：

```
用户在前端输入: "上个月华东区的销售额 Top10 产品"
│
│  ──── 第1步：请求进入 ────
│
│  [中间件链]
│    │ RequestContextMiddlewareCommon → 记录请求信息
│    │ RequestContextMiddleware → 记录操作上下文
│    │ ResponseMiddleware → 准备统一响应
│    │ TokenMiddleware → 验证 JWT Token → 提取当前用户
│
│  [API 路由]
│    │ POST /api/v1/chat/question
│    │ → chat/api/chat.py → question_answer()
│    │ → question_answer_inner()
│
│  ──── 第2步：初始化 LLMService ────
│
│  [chat/task/llm.py → LLMService.create()]
│    │ 1. 从 Chat 表获取对话信息
│    │ 2. 验证用户权限（是否有权访问该对话）
│    │ 3. 获取数据源配置（从 CoreDatasource 表）
│    │    ├── 如果已绑定 → 直接使用
│    │    └── 如果未绑定 → 进入数据源选择流程
│    │ 4. 获取 AI 模型配置 → LLMFactory 创建 LLM 实例
│    │ 5. 读取系统参数（行数限制、上下文轮数等）
│
│  ──── 第3步：智能匹配（Embedding）────
│
│  [术语表匹配]
│    │ terminology/curd/terminology.py
│    │ 问题 → Embedding → 匹配术语
│    │ 匹配到: "华东区" = 华东地区（包括上海、江苏、浙江、安徽）
│    │         "销售额" = 已开票的订单总金额（不含退款）
│
│  [SQL 示例匹配]
│    │ data_training/curd/data_training.py
│    │ 问题 → Embedding → 匹配相似示例
│    │ 匹配到: "各区域销售排名" → SELECT region, product, SUM(amount)...
│
│  [自定义 Prompt 匹配]
│    │ 查找工作空间级别的自定义 Prompt
│    │ 如: "请使用 company_schema 前缀"
│
│  ──── 第4步：构建 Prompt ────
│
│  [init_messages()]
│    │ 1. choose_table_schema()
│    │    ├── 如果启用表 Embedding → 语义匹配最相关的表
│    │    └── 获取表结构 + 字段信息 + 样本数据
│    │
│    │ 2. 组装消息序列:
│    │    [System] 角色定义 + SQL 规则
│    │    [Human]  详细规则（输出格式、安全限制）
│    │    [AI]     确认掌握规则
│    │    [Human]  <m-schema>表结构</m-schema>
│    │    [AI]     确认数据库信息
│    │    [Human]  <m-terminology>术语定义</m-terminology>
│    │    [AI]     确认术语信息
│    │    [Human]  <m-data-training>SQL示例</m-data-training>
│    │    [AI]     确认SQL示例
│    │    [Human]  历史对话（最近3轮）
│    │    [Human]  当前问题 + 当前时间
│
│  ──── 第5步：LLM 生成 SQL ────
│
│  [generate_sql()]
│    │ self.llm.stream(self.sql_message)
│    │ → 流式返回 LLM 输出
│    │ → process_stream() 解析 <think> 标签
│    │ → 每个 chunk 通过 SSE 推送给前端
│    │
│    │ LLM 返回:
│    │ {
│    │   "success": true,
│    │   "sql": "SELECT p.product_name, SUM(o.amount) as total_sales
│    │           FROM orders o
│    │           JOIN products p ON o.product_id = p.id
│    │           WHERE o.region IN ('上海','江苏','浙江','安徽')
│    │             AND o.order_date >= '2026-07-01'
│    │             AND o.order_date < '2026-08-01'
│    │             AND o.status = 'paid'
│    │           GROUP BY p.product_name
│    │           ORDER BY total_sales DESC
│    │           LIMIT 10",
│    │   "brief": "华东区上月销售额Top10",
│    │   "chart-type": "bar"
│    │ }
│
│  ──── 第6步：安全检查 ────
│
│  [check_sql()]
│    │ 1. 解析 JSON，提取 SQL
│    │ 2. sqlglot 解析 SQL → 检查写操作 → ✅ 只有 SELECT
│    │ 3. 检查危险函数 → ✅ 无危险函数
│    │ 4. 提取表名 → {orders, products}
│    │ 5. 表名权限检查 → ✅ 都在允许的表列表中
│
│  [权限过滤]（如果是普通用户）
│    │ get_row_permission_filters() → 获取行级权限条件
│    │ 如果有权限规则 → 再次调用 LLM 注入过滤条件
│    │ 如果没有 → 使用原始 SQL
│
│  ──── 第7步：执行 SQL ────
│
│  [execute_sql()]
│    │ db.py → get_session(ds) → 从连接池获取 Session
│    │ check_sql_read() → 最终安全检查
│    │ session.execute(text(sql))
│    │ → 返回查询结果:
│    │   [
│    │     {"product_name": "产品A", "total_sales": 150000},
│    │     {"product_name": "产品B", "total_sales": 120000},
│    │     ...
│    │   ]
│
│  ──── 第8步：生成图表 ────
│
│  [generate_chart()]
│    │ 构建图表 Prompt:
│    │   [System] 图表生成规则
│    │   [Human] 数据列 + SQL + 表结构
│    │   [Human] 当前问题
│    │
│    │ LLM 返回:
│    │ {
│    │   "type": "bar",
│    │   "title": "华东区上月销售额 Top10",
│    │   "columns": [{"name": "销售额", "value": "total_sales"}],
│    │   "axis": {
│    │     "x": {"name": "产品", "value": "product_name"},
│    │     "y": {"name": "销售额", "value": "total_sales"}
│    │   }
│    │ }
│
│  ──── 第9步：保存 & 返回 ────
│
│  [保存记录]
│    │ save_sql_exec_data() → 保存 SQL 结果到 ChatRecord
│    │ save_chart() → 保存图表配置
│    │ finish_record() → 标记完成
│
│  [SSE 推送完成]
│    │ yield {'type': 'finish'}
│
│  [日志记录]
│    │ 所有 LLM 调用的完整消息记录在 ChatLog 表中
│    │ 用于调试、审计、回溯
│
└── 前端收到数据，渲染图表展示给用户
```

## 4. 关键设计模式

### 4.1 分层架构

每个模块都遵循 `api → crud → models` 的分层模式：
- **API 层**：路由定义、参数验证、权限检查、响应格式化
- **CRUD 层**：业务逻辑、数据库操作
- **Model 层**：表定义、Schema 定义

### 4.2 工厂模式

`LLMFactory` 根据配置创建不同类型的 LLM 实例，新模型类型只需注册即可：
```python
LLMFactory.register_llm("new_model_type", NewModelLLM)
```

### 4.3 依赖注入

FastAPI 的 `Depends()` 机制贯穿始终，让 API 函数无需手动管理数据库连接和用户认证。

### 4.4 中间件模式

洋葱模型中间件处理认证、日志、响应格式化等横切关注点。

### 4.5 策略模式

`db.py` 中根据数据库类型选择不同的连接和执行策略（SQLAlchemy vs 原生驱动）。

### 4.6 流式处理

通过 Python 生成器 + SSE 实现 LLM 输出的实时推送。

## 5. 常见开发任务导航

| 你想做什么 | 需要看/改的文件 |
|-----------|----------------|
| 新增一个 API 接口 | 对应模块的 `api/xxx.py` + `apps/api.py` 注册路由 |
| 修改 Prompt 模板 | `templates/` 下的 YAML 文件 + `apps/template/*/generator.py` |
| 支持新的数据库类型 | `apps/db/constant.py` + `apps/db/db.py` + `apps/db/db_sql.py` |
| 支持新的 LLM 类型 | `apps/ai_model/model_factory.py` 注册新类型 |
| 调整 Embedding 匹配逻辑 | `apps/datasource/embedding/` + `apps/*/curd/` |
| 修改认证逻辑 | `apps/system/middleware/auth.py` |
| 添加新的系统参数 | `apps/settings/` + `alembic/versions/` 迁移 |
| 修改数据库表结构 | 新建 `alembic/versions/` 迁移文件 |
| 调试 NL2SQL 问题 | 查看 `chat_log` 表中的完整 Prompt 和 LLM 输出 |
| 调整 SQL 安全检查 | `apps/db/db.py` → `check_sql_read()` |
| 添加国际化文本 | `locales/` 目录下的翻译文件 |

## 7. 给新同学的建议

### 7.1 阅读顺序

1. **先读本文档（00-总览）** — 建立整体认知
2. **跑起来项目** — 启动后端，在前端提几个问题，观察日志
3. **读 01 + 02** — 理解项目结构和启动流程
4. **读 04（核心）** — 从 `chat/api/chat.py` 的 `question_answer()` 开始，跟到 `LLMService.run_task()`
5. **看 `chat_log` 表** — 这是理解 Prompt 最好的方式
6. **读 03 + 05 + 06** — 理解数据源、模型、Embedding
7. **读 07** — 了解系统管理的各个子模块

### 7.2 调试技巧

1. **查看 ChatLog 表**：每次 LLM 调用的完整 Prompt 和返回都记录在 `chat_log` 表中
2. **开启 SQL 调试**：设置 `SQL_DEBUG=true` 可以看到 SQLAlchemy 的 SQL 日志
3. **查看 uvicorn.log**：应用运行日志
4. **SSE 调试**：在浏览器开发者工具的 Network 面板可以看到 SSE 事件流

### 7.3 常见术语表

| 术语 | 含义 |
|------|------|
| NL2SQL | Natural Language to SQL，自然语言转 SQL |
| SSE | Server-Sent Events，服务端推送事件 |
| Embedding | 文本向量化，用于语义匹配 |
| Prompt | 给 LLM 的提示词/指令 |
| Schema | 数据库表结构描述 |
| OID | Organization ID，工作空间 ID |
| xpack | 扩展包（商业版功能） |
| MCP | Model Context Protocol，模型上下文协议 |
| LRU | Least Recently Used，缓存淘汰策略 |
| JWT | JSON Web Token，认证令牌 |
